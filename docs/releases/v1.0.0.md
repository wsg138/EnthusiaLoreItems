# EnthusiaLoreItems 1.0.0

EnthusiaLoreItems 1.0.0 is the first production release after the WP-04 release candidate and the WP-05 live acceptance program.

## Runtime baseline

- Java 21.
- Paper/Leaf-compatible Minecraft 1.21.11 server baseline.
- SQLite is the production persistence backend for this release.
- Geyser/Floodgate server-visible identity behavior is covered by WP-05 acceptance.

## Upgrade from 1.0.0-rc.1

1. Stop the server cleanly.
2. Take and verify a database backup before replacing the plugin jar. See `v1.0.0-rollback.md`.
3. Replace the RC jar with the verified `EnthusiaLoreItems.jar` from the `v1.0.0` release and verify its published SHA-256 checksum.
4. Start the server normally and verify LoreItems startup, schema initialization, queued-work recovery, and operator commands.
5. Run the repository-defined Sentinel `restart` verification profile for the deployed production artifact.

The production release is expected to open the RC database without destructive migration. Do not downgrade a database that has been used by 1.0.0 without restoring the matching pre-upgrade backup.

## Release contents

The GitHub release publishes the exact CI-verified shaded jar together with:

- SHA-256 checksum;
- CycloneDX JSON SBOM;
- Gradle runtime dependency manifest;
- normalized jar-entry manifest;
- deterministic profile evidence;
- automated test-report bundle;
- committed WP-05 acceptance index; and
- rollback instructions.

## Acceptance and release gate

Production publication is fail-closed. The `v1.0.0` release workflow consumes only the successful `main` CI artifact for the exact tag target and requires the committed WP-05 acceptance index to record:

- `Overall status: **PASS**`;
- `Evidence audit: **APPROVED**`; and
- `Owner/operator sign-off: **APPROVED**`.

The final acceptance index is the source of truth for exact case IDs, tested source head, jar SHA-256, GitHub run/evidence references, and review approvals. A green workflow alone does not substitute for that audit.

## Rollback

Rollback requires restoring the pre-upgrade database backup together with the prior verified RC jar. Do not simply put the older jar over a database that has already been opened and mutated by 1.0.0. Follow `v1.0.0-rollback.md` exactly.
