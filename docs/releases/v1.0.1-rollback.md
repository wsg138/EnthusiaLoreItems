# EnthusiaLoreItems 1.0.1 rollback instructions

These instructions cover reverting a failed production upgrade from `1.0.0` to `1.0.1`. The `v1.0.0` release is immutable and remains the prior production artifact.

## Before upgrade

1. Stop the server cleanly. Do not use a live SQLite database copy as the rollback source.
2. Preserve the complete LoreItems data directory, including `plugins/EnthusiaLoreItems/loreitems.db` and any SQLite sidecar files present after shutdown.
3. Record SHA-256 hashes for the backup and store it outside the live plugin directory.
4. Preserve the exact deployed `v1.0.0` `EnthusiaLoreItems.jar` and verify it against the published release checksum.
5. Record the current schema/startup state and verify the backup can be opened before changing the live installation.

## Roll back

1. Stop the server cleanly.
2. Move the failed 1.0.1 data directory aside; do not overwrite the only copy of it.
3. Restore the complete pre-upgrade LoreItems data backup to its original path.
4. Restore the exact verified `v1.0.0` jar from the immutable production release.
5. Start the server normally.
6. Verify LoreItems enables without SQLite integrity errors, queued work resumes as expected, public API registration is healthy, and representative tracked-item/delivery state is correct.
7. Run the repository-defined Sentinel `restart` verification profile against the restored deployment and require `PAPER_RESTART_OK`.
8. Retain the failed 1.0.1 data copy and logs for incident analysis until rollback is confirmed.

## Schema compatibility

Version 1.0.1 adds no database migration. Even so, use the matched pre-upgrade backup for rollback so operational writes made while the patch was active cannot silently change the logical state observed by 1.0.0.

## Prohibited shortcuts

- Do not retarget, overwrite, or replace assets on `v1.0.0`.
- Do not downgrade only the jar while assuming the live post-upgrade database is an equivalent rollback point.
- Do not treat a thermal/resource Sentinel gate or an incomplete restart as a successful rollback validation.

## Evidence to retain

Keep the pre-upgrade backup hashes, restored database integrity result, `v1.0.0` jar checksum, startup/restart logs, Sentinel result, and operator verification evidence with the release incident record.
