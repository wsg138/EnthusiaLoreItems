## Work completed

- Added a platform-free application `UnitOfWork` port with a transaction-scoped context.
- The initial transaction context exposes only the already-existing definition deletion compare-and-set mutation and audit append operation needed to prove the boundary. It does not add a command, GUI, deletion workflow, or public Bukkit API.
- Added `SQLiteUnitOfWork`, which runs callbacks on the existing bounded database executor, opens one connection through `SQLiteStorageRuntime`, and executes the callback through the shared `SQLiteTransactions` helper.
- Transaction-scoped operations are synchronous inside the callback so they do not enqueue nested database work or block the single database worker waiting on itself.
- The SQLite context becomes invalid immediately after its callback returns, preventing an escaped context from continuing to use the transaction connection.
- Nested unit-of-work execution on the database worker is rejected rather than being allowed to deadlock the single bounded worker.
- Refactored definition deletion SQL and audit insertion SQL into package-private transaction-scoped helpers reused by both the ordinary asynchronous repositories and `SQLiteUnitOfWork`.
- Hardened `SQLiteTransactions` so callback exceptions and errors trigger rollback, rollback failures are attached as suppressed failures, and auto-commit restoration failures do not silently replace an existing cause.
- Added focused SQLite integration tests proving both atomic commit and full rollback when the audit insert fails after the authoritative definition mutation has executed.
- Did not begin observation/current-state/anomaly persistence, campaigns/recipients, deleted-marker repositories, commands, item creation/adoption, inventory insertion, protection, tracking/reconciliation execution, GUIs, editing execution, deletion execution, or campaign execution.

## Important decisions and invariants

- Application code sees only `UnitOfWork`, transaction-scoped repository facets, domain types, and application records. JDBC and SQLite remain confined to the adapter.
- A transaction callback executes on the existing single bounded database worker and must use the supplied synchronous context. It must not call asynchronous repositories and wait for them.
- The context is valid only during the callback. Using an escaped context fails closed.
- The current context intentionally exposes one authoritative mutation plus audit append. Later repository families should extend the transaction context only when an actual atomic workflow requires them.
- The successful path commits both the definition state change and audit event.
- If audit persistence fails, the preceding definition mutation is rolled back and no audit event remains.
- No migration change was needed. The existing V1 tables and constraints are reused.
- The PR remains a draft and was not merged.
