## Substantive review findings

CodeRabbit review `PRR_kwDOTrktO88AAAABIVLZCw` completed with two actionable findings and one operational nitpick.

### 1. V1 duplicate rows could prevent V2 migration

The V1 schema permitted multiple `TEMPLATE_UPDATE` rows for the same non-null `instance_id` and `desired_revision`. Creating the new partial unique index without cleanup could fail during upgrade and leave storage degraded read-only.

Fix in `966ec62d0781d90682fc6fe226dfadd9349ebe23`:

- V2 now deterministically ranks duplicate rows before index creation;
- canonical selection prefers the most terminal/advanced state (`COMPLETED`, `REVIEW_REQUIRED`, `VERIFIED`, `APPLIED`, `CLAIMED`, then `PENDING`), then newer update time, greater attempt count, older creation time, and stable mutation ID;
- duplicate rows after rank one are removed in the same migration transaction;
- the partial unique index is then created;
- the upgrade regression seeds a pre-V2 duplicate pair and proves the completed canonical row survives and migration succeeds.

The schema contains no related foreign-key row keyed by `pending_mutations.mutation_id`, so canonical-row consolidation does not orphan linked mutation data.

### 2. `STARTED` accepted a rejected initial batch

`TemplateRevisionStartResult.started(...)` previously enforced non-null values but could still accept a batch result with a rejection status.

Fix in `966ec62d0781d90682fc6fe226dfadd9349ebe23`:

- `STARTED` now accepts only `SCHEDULED` or `COMPLETE` initial-batch states;
- a focused regression verifies rejected initial batches are refused.

Both inline review threads were automatically marked resolved after the fix commit.

### 3. Nonterminal work needs an eventual operator-unblock path

CodeRabbit also noted that a permanently nonterminal `TEMPLATE_UPDATE` can intentionally block later revisions. The concern is operationally valid, but implementing cancellation, expiry, monitoring, and operator resolution belongs with the PR 4b physical mutation worker and review controls.

This subphase deliberately remains fail-closed: bypassing nonterminal work before a verified resolution path exists could allow stale physical work to overwrite a newer template. PR 4b must therefore add bounded monitoring and an explicit operator resolution/cancellation path before the physical executor ships.
